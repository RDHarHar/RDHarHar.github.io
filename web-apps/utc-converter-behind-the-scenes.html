Behind the scenes - Code and lessons

I started with a clock.
Time had other plans.

I wanted a small, useful first web app. A time converter seemed like a good place to start. It was. It also had a few more moving parts than the two boxes in my sketch suggested.

By Ryan Harwick · September 15, 2026

I started with a sketch, then built the first version.

My first mockup was pretty basic: local time and UTC at the top, then two boxes underneath. I built the layout around that, added the live clocks, and connected the inputs to the conversion logic. Put a time in one side, get the other version out. A useful first entry under Web Apps.

Once the UTC conversion was working, I realized the other piece I had in mind was epoch time—the long string of numbers. I added timestamp parsing, then a separate form for converting a date back into epoch time. After trying the layout, I moved those tools below the original two panels.

My takeaway: get a small version working, use it, and build from there. I learn more from trying the code than staring at the sketch.

Three ways to describe the same moment.

I found it helpful to separate the moment itself from how I display it. Local time is what the clock says in my time zone. UTC gives me a shared reference. Unix epoch time counts from January 1, 1970 at midnight UTC.

The seconds-versus-milliseconds part matters. Two numbers can refer to exactly the same moment while one is a thousand times larger. I added an explicit unit selector and made the parsing code use that choice. Guessing based on the length of the number felt like a good way to create a very confident wrong answer.

I also kept the date attached to the time. A conversion that says “9:30 PM” is missing something fairly important if that means yesterday.

I want the inputs to say what they mean, and the outputs to show enough context that I don't have to guess.

Apparently, some times don't happen.

This was the interesting part. When clocks move forward, some local times are skipped. When they move back, some happen twice. A date and a time can look perfectly reasonable and still need another question before there's one correct answer.

I added a validation check for skipped times so the converter returns an error instead of silently moving the clock forward. For repeated times, I kept both possible results and added a first-or-second occurrence selector. That extra choice matters: the same local time can point to two different timestamps.

The tests also cover a half-hour clock change and a time zone with a quarter-hour offset. “Just add or subtract a few hours” stopped sounding like a complete plan pretty quickly.

The lesson I want to keep: when an input is ambiguous, make the choice visible. A clean-looking answer isn't useful if it's answering the wrong question.

I kept the moving parts separate.

I built the page with HTML for the structure, CSS for the layout and colors, and JavaScript for the clocks and conversions. Everything runs in the browser. There's no account, database, or server calculation involved in turning one time into another.

I kept the conversion rules separate from the code that responds to buttons and updates the results. That means moving the panels around doesn't require changing how the math works. The dedicated date-to-epoch panel can use the same conversion helpers as the original panels.

The colors come from the site's shared theme settings. I didn't want every new app to become its own little island with a different look and no way back to the rest of the site. Adding the full navigation to the converter was part of making it feel like it belonged here.

I want each part to have a clear job. It makes the next change easier to reason about, whether I'm changing the layout or adding another conversion.

I needed more than “looks right.”

A current-time conversion is a useful starting check. It doesn't tell me much about midnight, a leap day, a repeated hour, or a timestamp from before 1970.

I added 13 automated tests covering those kinds of cases, including invalid inputs, seconds and milliseconds, and time-zone changes. I also checked the page in the browser: do the buttons work, do the results update, and does the layout still fit on a small screen?

I also wired input changes to clear the previous result. It's a small bit of behavior, but it keeps an old answer from sitting there looking like it belongs to the new input.

I still rely on the device's clock and the browser's time-zone information. Those are useful boundaries to understand; passing a set of tests doesn't make the page independent of the system it runs on.

How I organized the code.

I split the app into a few small pieces so I can change one part without digging through everything else:

The conversion rules ↗Reading inputs, handling time zones, and translating epoch values. The page behavior ↗Live clocks, buttons, result updates, and validation messages. The layout ↗The panels, fields, and adjustments for smaller screens. The conversion tests ↗Examples that help catch mistakes when the code changes.

A small app, with a few lessons attached.

I started with a couple of boxes and a useful idea. The result gave me a better way to think about clear inputs, shared logic, and testing the awkward cases. That feels like a pretty good start for the first web app.

Building things. Breaking things. Learning along the way.
