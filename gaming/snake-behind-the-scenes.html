Behind the scenes - Code and lessons

A few squares.
A surprising number of rules.

I built Snake as the first little game for the site. Move around, eat food, get longer. Easy enough to describe. Making those three things behave properly gave me a few interesting problems to work through.

By Ryan Harwick · September 15, 2026

I started with the board.

I kept the first version small: a 20-by-20 grid, a snake, and one piece of food. Each snack adds 10 points, and the pace gradually increases. The walls stay solid. Running into myself still ends badly.

I used canvas to draw the board and regular HTML for the buttons and leaderboard. I also kept the game rules separate from the code that draws things and handles clicks. That let me test a move without needing the whole page running.

The game uses the site's existing colors and navigation. I wanted it to feel like part of the site, including when I switch themes or open it on a phone.

Giving the rules their own place made both testing and changing the interface easier.

My fingers can outrun the snake.

The snake moves in steps, but key presses can arrive between those steps. If I'm heading right and quickly press up, then left, those should become two separate turns. Applying both before the next move would send me straight back into myself. Efficient, but not particularly fun.

I added a small queue that remembers up to two turns and uses one per move. Each new turn is checked against the direction before it, so I can't reverse directly. Keyboard controls, direction buttons, and swipes all feed into the same rules.

When input and movement happen at different times, the order matters. A tiny queue can make the controls much more predictable.

The tail is already on its way out.

Checking whether the head hits the body sounds straightforward. There's one catch: on a normal move, the tail leaves its current square. Moving the head into that square is legal because the tail won't be there anymore.

I made the collision check leave out the departing tail. When the snake eats, it grows instead, so the tail stays and still counts as occupied. The difference is small in the code, but it changes whether a perfectly valid move ends the game.

Food placement had its own boundary case. I collect the empty squares and pick one, rather than repeatedly guessing a square until I get lucky. If there are no empty squares left, the board is full and the player wins. The game shouldn't spend forever trying to find somewhere to put lunch.

I needed to check what the board would look like after the move, not just what it looked like before it.

A pause button and a place to keep scores.

I schedule one move at a time. Pausing cancels the next move; resuming starts a fresh wait. I also pause when the tab is hidden or the window loses focus. Coming back to the game should give me a chance to play it.

For the leaderboard, I kept the top 10 runs in the browser's local storage. I can enter a name after a run and come back to those scores later in the same browser. They don't follow me to another device, and clearing browser data can remove them.

I check stored entries before displaying them and render player names as plain text. If storage isn't available, the game still works and keeps scores for the current visit. A scoreboard problem shouldn't stop the snake from moving.

Deciding where the data lives also decides what I can promise about it. This leaderboard is a personal score history, not a shared competition.

I tested the awkward moves.

I added six automated tests for quick turns, growth, wall and body collisions, moving into the departing tail, and filling the board. For the last one, a tiny two-by-two test board proves the rule without playing an entire game first.

I also checked the browser behavior: pausing, saving a score, reloading it, handling broken stored data, and fitting the page on desktop and small screens. Names that look like HTML should still appear as names.

Screenshot review caught a less exciting problem: some arrows had turned into question marks while the page was being written through a Windows shell. I replaced them with HTML character references so the intended symbols survive that step. Apparently, even the up button needs directions sometimes.

How I organized the code.

The pieces are small enough to follow individually:

The game rules ↗Movement, queued turns, food, collisions, and winning. The game in the browser ↗Drawing, controls, pausing, and saved scores. The layout ↗The board, leaderboard, and controls on smaller screens. The rule tests ↗Small examples for the moves most likely to cause trouble.

A small game was plenty to start with.

I got a playable game out of this, along with a better way to think about input timing, changes to game state, and testing boundaries. Now I just need to stop steering into the wall.

Building things. Breaking things. Learning along the way.
